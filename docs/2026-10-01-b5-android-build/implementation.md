## 2026-10-01 22:00 — Keeping adb and sdkmanager out of $HOME, for good

**adb.** The export's device probe started adb, which re-created `~/.android` (an empty dir,
then `adbkey` and `adbkey.pub`). The adb binary ignores ANDROID_USER_HOME and ANDROID_SDK_HOME
(its strings list only `ADB_VENDOR_KEYS`) and uses `$HOME/.android`. Fixes:
- `$ADB` is now a wrapper, `.tools/bin/adb`, generated by `android_env.sh`, that runs adb
  with `HOME=.tools/android-home`;
- the Godot import and export in `build_android.sh` run with the same `HOME`.

**sdkmanager** then re-created `~/.android/analytics.settings`, because it reads Java's
`user.home`. Fix: `JAVA_TOOL_OPTIONS` now also sets `-Duser.home=.tools/android-home`.

**Checked:**
- an adb start, an sdkmanager run and a full export, after which neither `~/.android` nor
  `~/.java` exists;
- `~/.config/godot` (the user's editor, dated 2026-09-24) was never touched.

**The leftover `~/.android`** files were from this session's tools only, and removing them
was within the user's approval.

**`RunController._sample_perf`** now also reports a **p95** frame time (the budgets are p95).

- The PERF line reads `frame avg X ms p95 Y ms max Z ms`.
- Desktop smoke (WSLg, uncapped, stress on Outpost): 7.7–7.9 ms avg, 10.0–10.5 ms p95,

**`scripts/android_perf.sh NAME SECONDS FLAGS…`** (new) runs one measured launch:
- a cold `am start -W`, with `ENGINE_ARGS` before the `--` for the renderer A/B;
- `CLIP=1` adds a screenrecord;
- after the wait it collects the logcat PERF lines, meminfo, thermal status and device props

## 2026-10-01 22:20 — The phone is paired; the first runs; launch flags

**The device.** Pairing went through `adb pair`, then `adb connect` (the user turned off
Samsung's **Auto Blocker**, which blocks wireless debugging). It's an **SM-S921B**:
- Exynos 2400 (s5e9945), Xclipse 940;
- Android 16;
- 1080×2340 at 120 Hz;
- 7.4 GB visible RAM.

**Launch flags don't arrive.** `am start --esa command_line_params …` reaches Android (the
ActivityTaskManager logs "has extras"), but Godot 4.7's `GodotActivity` logs
`Launch intent … with parameters []`, even for plain values. The key name is right
(`command_line_params` is in `classes7.dex`).
- **Fix:** **`LaunchArgs`** (new, `src/platform/launch_args.gd`). On Android debug builds it
  reads `user://launch_args.txt`, which `android_perf.sh` writes through `adb run-as` and
  deletes on exit.
- All four `OS.get_cmdline_user_args()` call sites now go through it.
- Two unit tests went into `platform_test`: parsing, and the file being ignored off Android.

**The renderer A/B.** `--rendering-method` can't be passed at launch either, so
`build_android.sh --renderer=compat` writes a `game/override.cfg` for that one export. The
preset includes it, `.gitignore` lists it, and a trap deletes it.

**adb reconnects.** The Godot export restarts the adb server, which drops the wireless
connection. `adb_ensure` (in `android_env.sh`) reconnects to
`.tools/android-home/last_device`.

## 2026-10-01 22:30 — On-device measurements (S24, debug APK)

Raw output is in `captures/perf/*.txt`. "Frame" is the interval between `_process` calls, and
"sim tick" is `TIME_PHYSICS_PROCESS`.

| Run | Renderer | fps | Frame avg / p95 / max (ms) | Sim tick (ms) | Draw calls | PSS |
| --- | --- | --- | --- | --- | --- | --- |
| Stress, 260 enemies | Mobile | 120 | 8.33 / 11.5 / 19 | 4.6–6.1 | 82–99 | 650 MB |
| Stress, 260 enemies | Compat | 120 | 8.33 / 12.0 / 21 | 5.1–7.1 | 82–101 | 384 MB |
| Canyon wave 10, full tree | Mobile | 120 | 8.33 / 10.0 / 19 | 2.3–3.7 | 112–184 | 628 MB |
| Canyon wave 10, full tree | Compat | 120 | 8.33 / 10.4 / 18.6 | 1.9–3.2 | 102–177 | 326 MB |
| Stress, **capped at 60** | Compat | 60.0 | 16.67 / 19.3 / 25.6 | 3.9–7.1 | 81–93 | **311 MB** |

- **Cold start:** `am start -W` TotalTime is **469 ms** (to the first frame; the campaign
  screen follows within about 2 s).
- **The renderer.** Both hold a locked 120 fps; the GPU isn't the limit on the S24.
  **Compatibility uses about half the memory**: graphics memory (GL mtrack) is about 300 MB on
  Mobile. On Samsung, Compatibility runs through ANGLE on Vulkan
  (`ANGLE ((Samsung Xclipse 940) on Vulkan 1.3.279)`). Decision: **switch to Compatibility**
  (`project.godot`, desktop included, so dev runs match the phone).
  - The canvas shaders (`enemy.gdshader`, `spotlight.gdshader`) compile and draw on both
    renderers: they were checked on desktop with `--tips`, and enemies draw correctly in a
    phone screenshot.
- **The 60 fps cap:** `application/run/max_fps.mobile=60`. Evenly paced at 60.0 fps.
- **The sim tick is the CPU risk.** The stress tick is 4–7 ms on the S24, against about 2 ms
  on desktop. A Helio G99 at ¼ the speed would need about 16–28 ms, which can't hold 60 fps
  under the synthetic 260-enemy load. Real content (wave 10, 30–40 enemies) is 2–3 ms here, so
  about 8–12 ms on the budget profile: it fits. Recorded in the ROADMAP as the open item.
  - Mobile CPU frequency scaling adds noise: an empty field once read 6.7 ms.
- **The Hive at wave 10:** the bot lost at wave 9 even with the full tree (no tree: Canyon
  lost at 7 and Hive at 5). So no boss-wave number this time. This is a measurement gap, not
  a perf finding.
